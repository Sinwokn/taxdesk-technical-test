# Hungarian VAT Declaration Generator

A small full-stack application that accepts invoice transactions as CSV, validates them, calculates Hungarian VAT (ÁFA) totals by category, and exports a reviewable PDF summary.

## Try it

### Docker (recommended)

```bash
docker compose up --build
```

Open <http://localhost:8080>. The application includes a **Use sample data** action, so the complete flow can be tested immediately.

### Local development

Prerequisites: .NET 8 SDK and Node.js 22+.

Terminal 1:

```bash
dotnet run --project backend/TaxDesk.Api --urls http://localhost:5080
```

Terminal 2:

```bash
cd frontend
npm ci
npm run dev
```

Open <http://localhost:5173>. Vite proxies `/api` calls to the ASP.NET Core API.

## Input contract

The source brief does not prescribe an input schema, so this implementation defines a deliberately small, explicit CSV contract:

| Column | Format | Notes |
|---|---|---|
| `invoiceNumber` | Text, 1–100 characters | Invoice or correction-note reference |
| `date` | `YYYY-MM-DD` | ISO calendar date |
| `netAmount` | Decimal | HUF; negative values represent corrections |
| `vatRate` | `0`, `5`, `18`, or `27` | Optional `%` suffix is accepted |

- UTF-8 comma-separated and semicolon-separated files are accepted.
- Semicolon-separated files may use Hungarian decimal commas (`1000,50`).
- Quoted CSV fields and escaped quotes are supported.
- Sample inputs live in [`samples`](./samples), and a valid sample is built into the UI.

## Calculation rules

- Currency is HUF.
- VAT is rounded **per transaction** to two decimal places using midpoint rounding away from zero.
- Category totals are sums of the rounded transaction values, avoiding the common discrepancy caused by rounding only at report level.
- Negative lines reduce the relevant VAT category and support correction notes.
- The PDF is a declaration **summary for review**, not an electronic NAV submission form.

## Architecture

```text
React + TypeScript
       │ multipart/form-data
       ▼
ASP.NET Core minimal API
       ├── strict CSV parser and row validation
       ├── decimal-based VAT calculation service
       └── in-memory PDF generator
```

The backend is organised by feature under `Features/VatReports`. Parsing, calculation, and PDF rendering have separate responsibilities. The production container serves the compiled React application and API from one origin.

### API

- `GET /api/health` — liveness check
- `POST /api/vat-reports` — returns a JSON summary
- `POST /api/vat-reports/pdf` — returns the generated PDF

Both POST endpoints expect exactly one `.csv` file as multipart form data.

## Reliability and security choices

- Uploads are processed in memory and never written to disk or retained.
- Request and file size are capped at 2 MB; row count is capped at 10,000.
- Input must be valid UTF-8 text; null bytes and binary content are rejected.
- Headers, dates, decimals, VAT rates, invoice reference lengths, and amount ranges are validated.
- Validation returns structured, row-level errors without exposing stack traces.
- All financial arithmetic uses `decimal`, never floating-point arithmetic.
- Upload endpoints are rate-limited per IP.
- The API applies restrictive CORS and browser security headers.
- The container runs as a non-root user with a read-only filesystem and no-new-privileges.
- The runtime has no third-party NuGet dependency; PDF output is generated by a small deterministic component.

## Verification

```bash
dotnet test backend/TaxDesk.Api.Tests/TaxDesk.Api.Tests.csproj
cd frontend && npm ci && npm run build
```

The backend test suite covers all supported VAT categories, per-line rounding and corrections, Hungarian decimal input, invalid rates, binary-content rejection, and PDF structure. CI repeats the tests, compiles the strict TypeScript frontend, and builds the production container.

## Trade-offs and next steps

For a time-boxed challenge, the application is intentionally stateless and does not add authentication or persistence. In production I would confirm NAV-specific reporting fields with tax-domain experts, version the input contract, add authentication and tenant isolation, perform malware scanning for broader file formats, persist auditable calculation snapshots, and add browser-level accessibility and end-to-end tests.
